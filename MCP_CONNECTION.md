# MCP connection checks

This is the persistent checklist for maintaining saveXtension’s copied connection prompt. Read it before changing `public/mcp-settings.js` or reviewing a connection incident. The copied prompt must carry the runtime checks itself: an agent in another app may not have this repository.

## Evidence and causal failure analysis

The user reported that a DeepSeek Harness (DSH) connection attempt assumed a bare server entry was valid in a patch file, wrote it without checking the required shape, and then waited without validating registration. No incident logs, exact configuration file, client version, or authoritative DSH schema were supplied. Do not invent those details or present a guessed DSH config block as a fix.

The reported chain was: an unverified schema assumption led to an invalid or ignored entry; no post-write validation exposed the problem; absent tools were treated as loading, extending the delay. The other risks below come from the user’s retrospective and gaps in the previous prompt; we have not independently established that each occurred in the incident.

| Cause or detection gap | Observable runtime check | Failure response |
| --- | --- | --- |
| Setup and “do not modify saves” instructions can be confused | Explicitly authorize the client configuration work, while prohibiting edits to saved posts, topics, and notes during setup | Continue authorized setup unless the user stops it; honor actual approval requirements and identify concrete blockers |
| Open-ended discovery | Identify the app/executable and installed version; inspect one authoritative installed reference or official documentation example within two minutes; allow one focused follow-up for a missing or mismatched version/schema | Report the unresolved fact and ask one precise question; do not guess or keep researching indefinitely |
| Unverified schema assumption, including a bare entry in a patch file | Before writing, record the minimal remote-MCP example, config scope/path, top-level shape, wrapper or operation path, and required fields | No write until that shape is established; JSON/TOML syntax alone is not schema validation |
| No validation after the write | Re-read the saved file and use the target client’s supported validator/status command; confirm the intended entry was parsed from the intended scope | Diagnose the actual error; repair only from verified schema evidence or revert only this attempt’s changes |
| A silently ignored entry looks like loading | Within 60 seconds after the documented reload/reconnect, confirm `savextension` is loaded and `library_overview` is registered in the client’s tools | Missing tools are a registration failure; do not extend the wait without new evidence |
| Success is claimed from a file write, HTTP response, or direct SDK test | Invoke `library_overview` through the target client’s MCP tooling in the active session and inspect a successful result | Report verification pending/failed, with exact stage and diagnostic; never claim connected from server reachability alone |

## Separate the two roles

- **Development agent:** reconstruct the incident from available evidence, map each cause to a gate, update the copied prompt and this checklist, then run the payload/clipboard tests. Prompt wording guides a runtime agent; these tests cannot force an arbitrary LLM to comply.
- **Runtime connection agent:** read the detected client’s actual version-matched schema, configure it, and produce evidence at each gate. Understanding an earlier incident does not establish another client’s schema.

The actual prompt is generated by `connectionPrompt(url)` in [public/mcp-settings.js](public/mcp-settings.js). Keep it client-neutral; DeepSeek Harness, OpenCode, Codex, Claude Code, and other clients must each supply their own authoritative example. A model/provider name is not sufficient evidence of the client being configured.

## Acceptance checks

1. **Identify:** actual client and installed version; intended user/project scope; no inference from the model name alone.
2. **Prove the shape:** cite an opened official page or installed schema/reference and locate its minimal Streamable HTTP example. Classify the actual shape before editing, such as an object map, wrapped map, patch-operation list, or a different structure established by the client’s schema. Verify wrapper keys, operation paths and required fields instead of translating from another client by analogy.
3. **Preserve:** adapt server name, the app-provided URL and documented no-auth behavior; preserve other servers, models, providers, credentials and unrelated settings. Do not echo credentials or put backups in version control. Skip the write when an existing correct entry can be reused.
4. **Validate:** re-read the result; check syntax and client-specific schema/loading separately. An exit status of zero without a parsed entry or registered tool is insufficient.
5. **Register:** use the documented reload/reconnect procedure once per evidenced change. Inspect the client’s status, warnings and registered tools; bound the registration wait to 60 seconds. A required client restart that cannot be performed in this session is **verification pending**, with the exact remaining step.
6. **Verify:** call `library_overview` from the target client’s MCP tooling, with a 60-second wait budget. Inspect the result for a tool/protocol error. A direct `curl` or SDK connection is useful diagnosis, not an in-client acceptance test.
7. **Report:** use **Connected and verified**, **Configured; verification pending**, or **Failed**. Include stage, elapsed time, config scope/path, validator or registration evidence, exact redacted diagnostics, and the next action. Do not include saved-post content or credentials in setup reports.

## Dry-run test plan

Use disposable client profiles and an isolated local library. Never edit the user’s real client configuration or use a paid AI session just to exercise these development checks.

| Scenario | Expected observable outcome |
| --- | --- |
| DeepSeek Harness, OpenCode, Codex, Claude Code: one supported installed version each | Agent identifies the client, opens that version’s real reference, extracts its minimal remote-server example and classifies its shape; no hard-coded schema is borrowed from another client |
| Patch-list fixture rejects a bare object | The schema gate prevents the write, or client validation detects the error immediately; no unbounded loading wait. This is an abstract regression fixture, not a claim about DSH’s current schema |
| Valid syntax but wrong wrapper, operation path, scope or enable field | Client loading/registration check fails even though a JSON/TOML parser accepts the file |
| Existing providers, credentials and other MCP entries | Diff contains only the necessary saveXtension change; unrelated values remain byte-for-byte where the client’s editing interface permits; secret values stay redacted |
| Already-correct server entry | No rewrite or duplicate registration; proceed to in-client verification |
| Missing or version-mismatched docs | Discovery ends within its budget, no speculative config is written, and the report names the unresolved fact |
| Endpoint reachable but client silently skips the entry | Registration fails within 60 seconds; a direct HTTP response cannot produce a success claim |
| Client requires restart or permission the agent cannot complete | Exact remaining action and **Configured; verification pending**; no claim that the active session is connected |
| Registered tool returns an error, or call times out | Report the exact redacted error/stage; do not label the connection verified |
| Successful connection | Target client invokes `library_overview` and gets a successful result; no saved posts, topics or notes are changed |
| Different local port | Clipboard contains the running app’s actual URL, with no assumed port or substituted address |

`tests/browser/mcp.spec.mjs` checks the copied payload and its gates, browser/native clipboard paths, feedback, and an isolated SDK-to-server round trip. These automated tests do **not** certify that DSH, OpenCode, Codex or Claude Code follows the prompt. Record each actual client/version and the evidence above when conducting the client dry runs; do not mark an unavailable client as passed.
